### Commit messages — no AI/LLM authorship attribution

Commit messages describe the **change**, not the tool that helped write it.
Do **not** add AI-assistant attribution to any commit:

- No `Co-Authored-By:` trailer naming a model or vendor
  (Claude, Opus, Sonnet, Haiku, GPT, ChatGPT, Copilot, Gemini, Codex, etc.)
  or a `noreply@anthropic.com`-style co-author address.
- No `🤖 Generated with ...` / "Generated by <AI tool>" footer.

This bans the **attribution trailer/footer only** — prose that legitimately
mentions a product as part of describing the change is fine (e.g.
"list codex alongside Claude Code as supported MCP clients").

A committed `commit-msg` hook enforces this. Git does not auto-enable
tracked hooks, so run this once per clone (see `.githooks/README.md`):

```bash
git config core.hooksPath .githooks
```

### run.ps1 convention — every QUAD application

Every QUAD application, sample, or standalone script **must** include two
files in its directory:

| File | Purpose |
|------|---------|
| `requirements.txt` | All Python deps with `>=` version pins |
| `run.ps1` | Generic uv-based dependency installer (not app-specific) |

`run.ps1` is always generic — it only creates a `.venv` with Python 3.10
and runs `uv pip install -r requirements.txt`. It never hard-codes a
script name, model path, or argument. The canonical template lives in
`QUAD-Client/.claude/skills/quad-run-ps1.md`.

The user runs the application separately after calling `run.ps1`:
```powershell
# One-time setup
.\run.ps1

# Run the app
.venv\Scripts\python.exe my_app.py --arg value
```

**Apply this automatically** whenever you create or scaffold:
- A new sample under `samples/`
- A generated app from `quad-codegen`
- Any standalone script in `examples/`

If `run.ps1` or `requirements.txt` already exist, update rather than replace.

## QUAD-Client Quick Commands

These commands run locally without spawning the QUAD MCP server.
Use the venv-explicit path so the command works regardless of which
Python is first on PATH in the Bash environment.

> **⚠️ NPU work uses a different interpreter than these CLI commands.**
> The local `.venv` here is an **emulated x86-64** Python (`platform.machine()`
> reports `AMD64` on this Qualcomm ARMv8 box). It is fine for the
> `quad_mcp_client.cli` commands below, but it **cannot load the Hexagon
> NPU wheels** (`onnxruntime-qnn`, `onnxruntime-genai`) — those are
> win-arm64-only. Any code that actually runs inference on the NPU must use
> the **native arm64** interpreter:
> ```
> C:\work\QUAD\QUAD\.venv-arm64\Scripts\python.exe
> ```
> The NPU stack is provisioned there (verified live on the Hexagon NPU,
> 2026-06). `onnxruntime-qnn` 2.x is a *plugin EP* — register it and select
> the NPU device via `get_ep_devices()` / `add_provider_for_devices()`; it
> does **not** show up in `get_available_providers()`. See the
> `quad-npu-prereqs` skill ("QNN EP usage") for the canonical snippet.
> Do **not** install NPU wheels into the x86 `.venv` — they will fail or
> silently fall back to CPU.

### `mcp__quad__*` tools unavailable / `/quad-convert`, `/quad-profile` failing (MCP registry, NOT connectivity)

**This is a different layer from the "MCP server connectivity check"
below — check this FIRST if `mcp__quad__convert_model`,
`mcp__quad__profile_workload`, `mcp__quad__hardware_detect`,
`mcp__quad__orchestrate_workload`, or `mcp__quad__generate_code` are
simply missing from the tool list** (not erroring — absent). Symptom:
`claude mcp list` shows `quad: ... - ✘ Failed to connect` or nothing at
all, even though `.claude/settings.json` has a correct `mcpServers.quad`
block and the server is independently reachable via `connect-test`.

**Root cause:** `.claude/settings.json`'s `mcpServers.quad` block alone
does **not** register the server with Claude Code's own MCP client
registry — that is a separate, explicit step. A prior attempt at this
step using `claude mcp add --transport sse-http ...` does NOT work and
leaves the server permanently in a failed state until removed.

**Fix — the exact working invocation** (confirmed live,
`docs/debugging/8. NPU_Profiling_MobileNetV2_IQ9075.md` §1):

```bash
# 1. Remove any stale/broken registration first (idempotent if absent):
claude mcp remove quad

# 2. Re-add with --transport http (NOT sse-http -- this is the fix):
claude mcp add --transport http quad "http://10.227.21.202:8000/mcp" \
    -H "Authorization: Bearer $QUAD_MCP_TOKEN"

# 3. Verify:
claude mcp list
# Expect: quad: http://10.227.21.202:8000/mcp (HTTP) - ✔ Connected
```

Resolve `$QUAD_MCP_TOKEN` first per step 2 of the connectivity check
below if it's not already in your shell.

**Caveat — a session restart may be needed.** Registering (or
re-registering) the MCP server mid-session does not always retroactively
populate the *current* Claude Code session's `mcp__quad__*` tool list.
If `/quad-convert` or `/quad-profile` still can't see the tools right
after running the above, try a call anyway before assuming a restart is
required — confirm the tools are genuinely absent (not just that
`claude mcp list` hasn't been re-checked) before recommending a
restart.

**Fallback while blocked (or across a restart you can't do mid-task):**
set `QAI_HUB_API_KEY` in `.env` (see `.env.example`) and use AI Hub
Models' cloud compiler / a pre-compiled on-device artifact directly
instead of waiting on `mcp__quad__convert_model` — this is what let NPU
profiling proceed in the report referenced above despite the MCP tools
being unavailable for that session.

### MCP server connectivity check

When the user asks "is this client connected to the MCP server", "can you reach QUAD", "is the MCP link up", or similar:

1. **Extract the URL and token env-var name from `.claude/settings.json`.**
   Read `mcpServers.quad` and pull:
   - the transport (`type`: `http` / `sse` → `sse-http`; `stdio` → `stdio-local`/`stdio-ssh`),
   - the URL string (`url`),
   - the token env-var NAME from `headers.Authorization`, which reads
     `"Bearer ${env:QUAD_MCP_TOKEN}"` — capture the identifier inside
     `${env:...}` (typically `QUAD_MCP_TOKEN`).

   You need the URL as a literal and the env-var NAME (not its value) for
   step 2. Do NOT skip this step: `connect-test` will accept a blank URL /
   token and produce a misleading failure — escalation #63 confirmed this
   is the most common mis-triage on this repo.

2. **Get the token value.** `install.ps1` writes the token into a
   User-level Windows env var (e.g. `QUAD_MCP_TOKEN`) and references it
   from `settings.json` via `${env:...}`. It does **NOT** write it into
   `.env` — `.env` is often empty even on correctly configured projects.
   So:
   - First try the current shell: `echo "$QUAD_MCP_TOKEN"` (or the name
     you captured in step 1). If it prints a hex string, use it.
   - If empty, the User env var isn't inherited by this Bash session.
     Read it directly:
     ```bash
     powershell -NoProfile -Command "[System.Environment]::GetEnvironmentVariable('QUAD_MCP_TOKEN','User')"
     ```
     Export the result: `export QUAD_MCP_TOKEN=<value>`.
   - As a last resort, `.env` may hold it if the user copied `.env.example`
     and filled it in — but this is not the install.ps1 default.

3. **Run the live check** with the resolved URL and token as literals:
   ```bash
   .venv/Scripts/python.exe -m quad_mcp_client.cli connect-test sse-http \
       --sse-url "<literal-url-from-step-1>" \
       --auth-token "<literal-token-from-step-2>"
   ```
   (`sse-http` is the common case for the hosted MCP server; use
   `stdio-local` / `stdio-ssh` if `settings.json` declares them — run
   `connect-test --help` for the exact flags.) The CLI now rejects blank
   URL / token up front (issue #63) so a misfired variable expansion
   fails loud rather than silently probing "".

4. If `connect-test` succeeds, report the handshake result (it includes
   server version) — done.

5. If it fails, triage in this order (fastest signal first):
   - `curl -H "Authorization: Bearer $QUAD_MCP_TOKEN" <url>` — isolates
     raw transport / network / auth failures (most common cause).
   - `.venv/Scripts/python.exe -m quad_mcp_client.cli status` — confirms
     `settings.json` is present and correctly wired.
   - `.venv/Scripts/python.exe -m quad_mcp_client.cli doctor` — checks
     local SDK / env issues on this machine.
   - `quad.toml` — check adapter-level config (e.g. AI Hub Models key /
     URL) if the failure is adapter-specific rather than transport-level.

### Profile a local board via a remote/cloud MCP server (`profile-device`)

When the user wants to profile a model on a board attached to **this** machine
but the MCP server is remote (cloud), the server can't reach the board. Use the
client-side agent, which asks the server for a plan, runs it locally over your
SSH/ADB, and posts results back for a comprehensive report:

```bash
.venv/Scripts/python.exe -m quad_mcp_client.cli profile-device \
    --model ./model.bin --transport ssh --host root@<board-ip>
```

The model file must be local (where the board is). `.bin`→qnn-net-run (NPU),
`.dlc`→snpe-net-run, `.onnx`→exploratory on-device onnxruntime. Add `--json` for
the full report. This is the "cloud server + local device" path; the server-side
`mcp__quad__profile_device` only works when the server itself can reach the device.

The model can also come **from the server** — you rarely have a Qualcomm `.bin`
locally, you get it from a conversion. Two extra source modes (pick exactly one
of `--model` / `--model-from-server` / `--convert`; both server modes need a
hosted `--url`/settings.json server):

```bash
# (a) profile an artifact a prior convert produced (paste its download_url):
… profile-device --model-from-server "/bundles/<id>/download?d=…&h=…" --sha256 <hash> \
    --transport ssh --host root@<board-ip>

# (b) convert/quantize on the server, then profile the result on your board — one command:
… profile-device --convert --model ./model.onnx --source-format onnx \
    --target-sdk qnn --quantization int8 --transport ssh --host root@<board-ip>
```

`--convert` uploads the local source, runs `convert_model` on the server,
auto-downloads the produced `.bin`/`.dlc` to the client, then profiles it on the
board. The fetched artifact is deleted after unless you pass `--keep`.



### Board connect (IQ-9075)

When the user says "SSH into the IQ-9075", "connect to the board", or similar, with Wi-Fi/SSH already configured (see `docs/IQ9075_SOPs.md` for first-time bring-up): SSH is the validated, default transport for this board (~95% of workflows; ADB is a Wi-Fi-bootstrap-only fallback, not needed here).

1. Read connection details from `.env_boards` (`IQ9075_HOST`, `IQ9075_SSH_USER`, `IQ9075_SSH_PASSWORD`, `IQ9075_PLINK_PATH`, `IQ9075_SSH_HOST_KEY_FINGERPRINT`) — copy from `.env_boards.example` if it doesn't exist yet. Never hardcode these values inline.
2. OpenSSH was tried first and rejected — Windows' built-in OpenSSH client has no way to feed a password non-interactively (no `-pw`-equivalent flag) and this board only offers password auth, so it fails with `Permission denied (publickey,password)`; PuTTY's `plink.exe` supports `-pw` for exactly this case:
   ```bash
   "$IQ9075_PLINK_PATH" -ssh -pw "$IQ9075_SSH_PASSWORD" -batch -hostkey "$IQ9075_SSH_HOST_KEY_FINGERPRINT" "$IQ9075_SSH_USER@$IQ9075_HOST" "<command>"
   ```
   The host key fingerprint changes on every reflash — on first connect after a reflash, `plink` prints the new fingerprint; re-accept it and update `.env_boards`.
3. `quad-client unoq status/deploy/...` (the `SSHTarget`-based commands in `src/quad_mcp_client/local/board/ssh.py`) do **not** work against this board yet — `SSHTarget.base_args()` hardcodes `BatchMode=yes` (key-only auth), and the IQ-9075 is currently password-auth. Use `plink` directly per step 2, or provision an SSH key on the board first if key-auth becomes available.

Full RCA on why SSH (not ADB) is the default here: `docs/debugging/`.
