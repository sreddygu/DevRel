WIN Connectivity Issues - Triage Summary

1. What Happened

Observed Symptom
Repetitive client disconnection pattern on 6G band - STA fc:b3:bc:f0:b0:c2
experiences rapid connect/disconnect cycles despite successful authentication and key
exchange.
Supporting Log Evidence
Thu Nov 13 12:01:30 2025 - SAE auth success (status_code=126/H2E)
Thu Nov 13 12:01:31.454 - mld0: STA fc:b3:bc:f0:b0:c2 IEEE 802.11: disassociated [DISCONNECT #1]
Thu Nov 13 12:01:32.798 - mld0: STA fc:b3:bc:f0:b0:c2 IEEE 802.11: disassociated [DISCONNECT #2]
Context
Band: 6G (wifi1, 5180 MHz, link_id=2)
Role: AP (mld0 interface)
Security: WPA3-SAE with H2E (Hash-to-Element)
Environment: Multi-Link Device (MLD) configuration
Pattern: 3 disconnections within 3 seconds

2. Root Cause Analysis

Primary Suspected Causes (Ranked by Likelihood)
HIGH - Client Inactivity Timer/Keepalive Failure
Pattern matches KB reference: Section 7.1 "Disconnection initiated by AP - kickout
STA"
No explicit deauth reason codes in logs
Clean DEL_STATION operations suggest AP-initiated removal
Timing (~1.3 seconds) consistent with aggressive keepalive timeout
MEDIUM - MLO Link Management Issue
MLD configuration with link_id=2
Possible MLO self-roaming or link state synchronization failure
KB reference: Section 6.3 "MLO self-roaming"
LOW - RF/PHY Layer Issues
Some TX retries observed (tx_xretry: 41)
RSSI values adequate (-30 to -36 dBm)
No significant PHY errors reported

3. Why This Root Cause Fits

Specific Reasoning
Evidence Supporting Inactivity Timer:
Log Sequence: Successful auth → 4-way handshake complete → ~1.3 second delay
→ disassociation
No Explicit Reason: Missing deauth/disassoc reason codes typically indicates timeout based removal
Stats Correlation:
flush_errs[38]: 191 indicates client removal flush (KB:
WIFIFLUSH_REQUEST_STA_PEER_DEL)
Management frame counters show normal auth/assoc but elevated disassoc
Consistent Pattern: Exact timing repetition (1.3 seconds) suggests timer-based trigger
KB Pattern Match: Per WIN_Connectivity Issues handbook Section 7.1:
"Check if STA inactive time reached threshold"
"vdev_id:1 assoc_id:172 is_primary 1 hw_link_id 2 Master link inactivity"
Matches observed MLD link_id=2 configuration

4. Mitigation / Next Steps

Immediate Low-Risk Mitigations
1. Adjust AP keepalive timer (if aggressive):
cfg80211tool mld0 link_id 2 set_inact 30 # Increase to 30 seconds
2. Disable MLO-specific optimizations temporarily:
cfg80211tool mld0 link_id 2 mlo_peer_pref 0
3. Enable powersave tolerance:
cfg80211tool mld0 link_id 2 wnm_sleep 1
Verification Steps
1. Enable enhanced debug logging:
cfg80211tool mld0 link_id 2 dbgLVL 0x80c00000 # MLME debug
cfg80211tool mld0 link_id 2 csl 1 # Console logs
cnss_diag -pc | grep -e VDEV_MGR_AP_KEEPALIVE -e STA_KICKOUT
2. Capture keepalive statistics:
wifistats wifi1 11 --mac fc:b3:bc:f0:b0:c2 | grep inactive_time
3. Monitor MLO state transitions:
cfg80211tool mld0 link_id 2 sm_history
Escalation Actions
If issue persists after mitigations:
1. Capture OTA packet trace to verify client TX activity
2. Collect pktlogconf during disconnect event
3. Check for firmware-specific MLO bugs in release notes
