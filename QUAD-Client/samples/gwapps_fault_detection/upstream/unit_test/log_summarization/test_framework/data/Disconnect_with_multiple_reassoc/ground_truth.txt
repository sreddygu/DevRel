2. Root Cause Analysis

Primary Hypothesis (HIGH Likelihood)
Driver-initiated disconnection due to MLO link management failure
Evidence Supporting This:
1. Hostapd logs show driver-initiated DEL_STATION event:
nl80211: Drv Event 20 (NL80211_CMD_DEL_STATION) received
This precedes the hostapd disassociation message
[[Knowledge: WIN_Connectivity Issues - Wifi Debug handbook|Disconnection
initiated by AP|quote:"AP sends Deauth/Disassoc to STA"|context:The
DEL_STATION event from driver indicates AP-side initiated disconnection]]
2. Consistent ~1 second connection duration:
Connection durations: 0.988s, 1.000s, 0.974s
Suggests timer-based disconnection mechanism
Not random failures
3. MLO link alternation pattern:
Disconnections alternate between link_id:1 (6G) and link_id:2 (5G)
Indicates MLO coordination issue
Alternative Hypothesis (MEDIUM Likelihood)
TX path issues causing station kickout
Evidence:
WiFiStats showing TX anomalies:
mpdus_ack_failed = 134
tx_xretry = 133
hw_flush = 269
flush_errs = 254 (error code 38)
mpdu_requeued = 3588
[[Knowledge: WIN_Connectivity Issues - Wifi Debug handbook|Tx path
stability|quote:"Check FW/HW data frame tx status"|context:High TX retry and flush
errors can trigger station kickout due to excessive retries]]
Alternative Hypothesis (LOW Likelihood)
Client-side deauth after connection
Evidence against this:
Hostapd shows: Station fc:b3:bc:f0:b0:c2 trying to deauthenticate, but it
is not authenticated
Deauth frame arrives AFTER the DEL_STATION event
Indicates client responding to disconnection, not initiating it
